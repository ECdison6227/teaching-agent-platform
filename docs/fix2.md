# FIX2 验收与吞吐排查

## 修复

- 结构、OCR/要点、讲义、习题统一优先使用 JSON 模式，通道明确不支持时降级；解析器容忍围栏、前后文字、LaTeX 反斜杠和非法转义。截断内容拒绝猜补，重新请求完整 JSON，解析/校验至少重试两次。
- provider 统一对网络错误、超时、408、429、5xx 指数退避重试三次，附带抖动。网络预算耗尽后不会再乘上解析预算。模型失败只降级当前项目，记录待核对；其他讲义/习题批次继续。
- 页图/文本转换和 OCR 结果缓存在 DATA_DIR，课程页面提前入库。结构、讲义和习题批次使用课程维度检查点；每批习题与检查点同事务提交，包括零题目批次。续跑跳过已有要点、非空讲义和完成批次，保留 ID 与审核内容；兼容旧导入已入库的数据。
- 导入中/失败的课程也渲染学习空间，显示进度或错误并提供“从失败处继续”，自学天地可以翻阅已有页图与要点。知识点结构使用温度 0.2，数量随页数变化，校验概念标题及连续、不交错、不重复且完整的页段。

## 吞吐结论与证据

1. 并发池确实生效：实际 HTTP mock 验证文本页配置 2 路、扫描页默认 4 路，最大在途请求分别为 2 和 4；较慢的第一页不会阻塞其他页完成。
2. 一页只执行一次成功的要点生成；扫描页的 OCR 与要点共用一个结构化响应，随后复用缓存。失败重试会增加请求次数，旧实现未记录次数，容易把重试耗时算作正常单页耗时。
3. 要点入库是短同步事务，不在网络等待期间持有 SQLite 写锁。本机 mock 测试中每页入库耗时中位数低于 1 ms，模型请求耗时占主要部分；没有观察到本机写锁造成秒级延迟。文件转换和结构划分有阶段边界，讲义逐项处理，但它们不在逐页要点的并发循环内，不会使该循环逐渐串行。
4. 只读核查历史日志，没有逐页请求耗时、重试计数或 HTTP 状态统计；日志也未记录 429。旧数据末段的平均文本长度和页图大小均小于前段，未发现输入体积增长能够解释减速的证据。**无法追溯证明从约 13 秒/页变为约 23 秒/页的具体上游原因，也不能据此断言发生限流。** 已排查并发失效、重复 OCR 和明显的本机写入瓶颈；上游推理/排队波动及失败重试是剩余候选，需要新日志确认。
5. 新增 `import_page` JSON 日志记录每页总耗时、模型耗时、入库耗时、请求数、网络/解析重试数及 429/5xx 次数，区分转换、要点与缓存命中。`model_retry` 记录重试序号及状态，不打印原文、提示词和密钥。后续可直接区分上游响应变慢、明确限流、重试放大和本地写入耗时。

## 续跑

在仓库根目录使用 Node 22+，保持与 Web/worker 相同的 DATA_DIR：

```bash
npm run import:resume -- <courseId>
```

CLI 直接执行指定课程的新建/排队任务；已有活跃 worker 时不重复执行，已完成课程直接退出。异常退出的 worker 需等心跳五分钟过期。自动降级的项目已标为待核对，续跑会保留它们。
